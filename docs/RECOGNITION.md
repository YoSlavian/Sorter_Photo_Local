# Что распознаётся в тексте

Справочник маркеров, по которым строится схема из описания на естественном
языке. Все маркеры собраны в `src/bpmn_architect/parsing/lexicon.py` — сам
парсер не содержит слов ни одного языка.

Чтобы увидеть, как разобрано конкретное описание:

```bash
bpmn-architect explain описание.txt
```

## Границы процесса

| Формулировка | Результат |
|---|---|
| `Процесс начинается с ...`, `Процесс стартует ...`, `Начало процесса`, `Триггер: ...` | стартовое событие |
| `The process starts when ...`, `Triggered by ...`, `Begins with ...` | то же |
| `Процесс завершается.`, `Конец процесса`, `На этом процесс окончен` | конечное событие |
| `The process ends`, `The process is complete` | то же |

Текст после маркера становится названием события; форма приводится к
именительному падежу (`начинается с получения заявки` → «Получение заявки»).
Тип триггера определяется по тексту: «уведомление», «заявка», «сообщение» →
событие-сообщение; «через 3 дня» → таймер; «ошибка», «сбой» → событие-ошибка.

## Шаги и исполнители

Исполнитель распознаётся в четырёх формах, в порядке убывания явности:

```text
[Кладовщик] комплектует заказ        явная форма
Бухгалтер: формирует платёжное пор.  форма с двоеточием
Менеджер проверяет заявку            роль + глагол
X is done by the manager             пассив (англ.)
```

Роль должна входить в словарь ролей (`ROLE_STEMS`: менеджер, бухгалтер, юрист,
оператор, отдел, служба, система, department, manager, …) — это осознанное
ограничение в пользу точности: произвольное слово с заглавной буквы
исполнителем не считается.

Шаг без указанного исполнителя наследует исполнителя предыдущего шага
(`--no-lanes` отключает дорожки целиком, `ParserOptions.inherit_actor` —
только наследование).

### Тип задачи

| Признак в тексте | Тип |
|---|---|
| `система`, `автоматически`, `сервис`, `интеграция`, `API`, `робот` | `serviceTask` |
| `отправляет`, `направляет`, `уведомляет`, `sends`, `notifies` | `sendTask` |
| `получает`, `принимает`, `receives` | `receiveTask` |
| `по правилам`, `бизнес-правила`, `скоринг`, `регламент`, `decision table` | `businessRuleTask` |
| `вручную`, `manually` | `manualTask` |
| `скрипт`, `script` | `scriptTask` |
| `подпроцесс`, `sub-process` | `subProcess` |
| есть исполнитель-человек | `userTask` |
| ничего из перечисленного | `task` |

### Именование

Формулировка приводится к конвенции BPMN — «глагол в инфинитиве + объект»:

```text
Менеджер проверяет заявку        → задача «Проверить заявку», дорожка «Менеджер»
Бухгалтер формирует счёт          → задача «Сформировать счёт»
The recruiter creates the record  → задача «Create the record», дорожка «Recruiter»
```

Если форма глагола неизвестна — текст остаётся как есть. Полное отключение —
флаг `--verbatim-names`.

## Ветвления

### В одном предложении

```text
Если заявка корректна, то бухгалтер выставляет счёт, иначе менеджер отклоняет заявку.
Если сумма больше лимита — требуется согласование директора.
If the amount is above the limit, then the director approves it, otherwise the manager does.
```

Открывающие маркеры: `если`, `в случае если`, `при условии что`, `когда`,
`в зависимости от`, `if`, `when`, `in case`, `depending on`.
Разделители: `, то`, `, тогда`, `then`, ` — `.
Альтернатива: `иначе`, `в противном случае`, `если нет`, `в остальных случаях`,
`otherwise`, `else`, `if not`.

Ветки получают метки «Да»/«Нет» (`Yes`/`No` для английского); отрицательная
ветка помечается **потоком по умолчанию**. Если альтернатива не описана, ветка
«Нет» проходит напрямую к слиянию.

### Блочная запись

```text
Если договор согласован:
    Руководитель подписывает договор.
    Бухгалтер регистрирует договор.
Иначе:
    Юрист дорабатывает проект.
Менеджер отправляет договор контрагенту.
```

Вложенность — по отступу или по нумерации (`2.1` вложено в `2`). Строка без
отступа, не являющаяся альтернативой, закрывает ветвление и продолжает основной
поток.

### Несколько вариантов списком

```text
Оператор определяет категорию обращения:
  - Техническая: инженер устраняет неисправность.
  - Финансовая: бухгалтер проверяет платежи.
  - Прочая: оператор готовит ответ клиенту.
```

Заголовок, который *выполняет действие*, даёт **два** элемента: задачу
«Определить категорию обращения» и шлюз «Категория обращения?» — именно так
разложил бы это аналитик вручную. Заголовок-вопрос (`Заявка корректна?`) даёт
только шлюз.

## Параллелизм

```text
Параллельно выполняются проверка склада и проверка кредитного лимита.
Проверка склада и проверка лимита выполняются одновременно.
In parallel the IT department prepares the workplace and the manager prepares the plan.
```

Маркеры: `параллельно`, `одновременно`, `в то же время`, `синхронно`,
`in parallel`, `simultaneously`, `concurrently`, `at the same time`.
Перечисление разбивается по `и`/`and`/запятым; создаются парные параллельные
шлюзы.

## Слияние потоков

```text
После этого менеджер уведомляет клиента.
В любом случае заявка регистрируется.
После завершения обеих проверок формируется отчёт.
Once both are complete, the report is generated.
```

Маркеры: `после этого`, `после чего`, `в любом случае`, `в обоих случаях`,
`независимо от результата`, `потоки объединяются`, `after that`, `in both
cases`, `once both are complete`, `regardless of the outcome`.

Маркер закрывает все открытые блоки на своём уровне и продолжает основной поток.
Простые связки (`затем`, `далее`, `потом`, `then`, `next`) смысловой нагрузки не
несут и просто отбрасываются.

## Циклы и возвраты

```text
Заявка возвращается к проверке заявки.
Документ отправляется на доработку и возвращается к шагу 2.
The request goes back to the verification step.
```

Маркеры: `возвращается к`, `возврат к`, `вернуться к`, `повторить`,
`направляется обратно к`, `return to`, `go back to`, `loop back to`, `repeat`.

Цель ищется в три приёма: по номеру шага (`шаг 2`, `step 2`), по точному
названию элемента и по нечёткому совпадению словарных основ. Не найденная цель
даёт диагностику `B201`, а путь закрывается конечным событием — сборка не
прерывается.

## Ожидание и промежуточные события

```text
Менеджер ожидает подтверждения от клиента.   → событие-сообщение
Система ждёт оплаты счёта.                    → событие-сообщение
Через 3 дня заявка закрывается автоматически. → событие-таймер (P3D)
Ежедневно формируется отчёт.                  → таймер-цикл
```

Маркеры ожидания: `ожидает`, `ждёт`, `в ожидании`, `waits for`, `awaits`,
`pending`. Таймеры: `через N <единица>`, `в течение N ...`, `по истечении`,
`ежедневно`/`еженедельно`/`ежемесячно`, `after N days`, `within N hours`,
`daily`/`weekly`/`monthly`. Числовые выражения переводятся в ISO-8601.

## Структура документа

* Первая строка без глагола и без маркеров считается названием процесса
  (если строк больше одной).
* `Процесс: Название` и `Название процесса: ...` — явное название.
* Маркеры списка (`-`, `*`, `1.`, `2.1.`) распознаются и отбрасываются, но
  нумерация учитывается как вложенность.
* Предложения внутри строки разделяются с учётом сокращений (`т.д.`, `руб.`,
  `e.g.`) и десятичных дробей.
* Строки, начинающиеся с `#` или `//`, — комментарии.

## Порядок разбора

Маркеры проверяются в фиксированном порядке, и он важен:

1. слияние потоков;
2. **ветвления** — условное предложение владеет всем своим текстом;
3. параллелизм;
4. разделение сочинённых клауз (`... и заявка возвращается к ...`);
5. границы процесса;
6. переходы;
7. ожидание;
8. обычный шаг.

Ветвления проверяются раньше границ процесса намеренно: в предложении
«…иначе менеджер отклоняет заявку и процесс завершается» маркер конца стоит
внутри ветки и при более раннем разборе поглотил бы всё ветвление. Ветки
условия затем разбираются рекурсивно, как самостоятельные предложения.

## Если формулировка не распознана

Предложение всё равно попадёт в схему — как задача с исходным текстом. Ничего не
теряется; `explain` покажет, что получилось, а `validate` укажет на структурные
последствия.
