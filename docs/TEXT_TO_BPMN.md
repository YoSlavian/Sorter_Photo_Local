# Как текст превращается в BPMN

Документ описывает конвейер целиком. Полный справочник распознаваемых
формулировок — в [RECOGNITION.md](RECOGNITION.md), синтаксис DSL — в
[DSL.md](DSL.md).

```
текст ─интерпретация─▶ IR ─сборка графа─▶ модель ─проверка─▶ диагностика
                                             │
                                             └─компоновка─▶ геометрия ─▶ BPMN 2.0
```

## Три режима интерпретации

Выбираются в верхней панели; на конвейер ниже они не влияют — все три отдают
одно и то же промежуточное представление.

### Детерминированный (по умолчанию)

Правиловый разбор: словарь маркеров, морфология, стек блоков. Никаких сетевых
вызовов, никаких ключей, полная воспроизводимость — одно описание всегда даёт
побайтово одинаковый файл.

Это единственный режим, пригодный для версионирования диаграмм в git и для
сборки в CI.

### AI

Языковая модель читает описание и отвечает **на DSL этого проекта**, а не
JSON'ом и тем более не BPMN-ом. Ответ разбирается тем же проверенным парсером
DSL, что и написанный человеком.

Причина такая: модель может выдать синтаксически безупречный JSON, который как
процесс является бессмыслицей; DSL же упирается в настоящую грамматику с
настоящими сообщениями об ошибках. Гарантию корректности даёт парсер, а не
промпт. Если ответ не разобрался, модель получает обратно текст ошибки парсера
и вторую попытку; если и она не удалась — вызов завершается ошибкой, а не
повреждённой диаграммой.

### Гибридный

1. разобрать детерминированно;
2. поискать, что описание оставило неоднозначным;
3. **если ничего — вернуть детерминированный результат без вызова модели**;
4. иначе показать модели текст, детерминированное прочтение и список открытых
   вопросов и попросить исправленную версию.

Третий шаг — самое важное: на хорошо написанных описаниях гибридный режим
ведёт себя ровно как детерминированный, не тратя ни токена. Если провайдер не
настроен или ответ непригоден, режим возвращается к детерминированному
результату с пометкой в `meta.notes`, а не падает.

### Подключение модели

Ядро не зависит от конкретной модели. Провайдеры — необязательные пакеты:

```bash
pip install "bpmn-architect[anthropic]"   # Claude
pip install "bpmn-architect[openai]"      # OpenAI
pip install "bpmn-architect[openai]"      # и любой OpenAI-совместимый сервер
```

```bash
export BPMN_ARCHITECT_LLM_PROVIDER=anthropic
export ANTHROPIC_API_KEY=...
# локальная модель:
export BPMN_ARCHITECT_LLM_PROVIDER=local
export BPMN_ARCHITECT_LLM_BASE_URL=http://localhost:11434/v1
```

Свой провайдер добавляется одним классом с методами `available()` и
`complete()` — см. [EXTENDING.md](EXTENDING.md).

## Промежуточное представление

Оба фронтенда (текст и DSL) собирают одно **блочное дерево**: ветвления и
параллелизм — вложенные блоки, а не пара «развилка/слияние».

Отсюда важное следствие: парсер физически не может породить несбалансированный
шлюз, потому что слияние создаёт тот же код, который создал развилку. Целый
класс ошибок исключён конструктивно.

## Сборка графа

Обход дерева несёт список **открытых портов** — выходов, которым ещё нужен
адресат. Блок принимает переданные порты и возвращает те, что оставляет
открытыми.

Частные случаи получаются бесплатно: если одна ветка условия заканчивается
конечным событием, выживает единственный путь — и лишнее слияние не создаётся.
Ровно так нарисовал бы человек.

Возвраты («вернуться к проверке заявки») разрешаются вторым проходом: по якорю,
по номеру шага, затем по нечёткому совпадению словарных основ с названиями
элементов.

## Неоднозначности

Инструмент не додумывает молча. Если описание чего-то не сказало, появляется
вопрос с конкретными вариантами, собранными из уже известного — например,
«Кто выполняет действие?» с перечнем уже найденных ролей.

Распознаются четыре вида пробелов:

| Вид | Когда возникает |
|---|---|
| `actor` | у задачи нет исполнителя, хотя дорожки в процессе есть |
| `naming` | шаг назван, но ничего не говорит: «Обработка», «Выполняется проверка» |
| `condition` | у расходящегося шлюза нет вопроса |
| `branch_label` | у ветки нет ни названия, ни условия |

Ответы применяются **к модели, а не к тексту**: авторское описание остаётся
записью того, что было написано.

## Карта соответствий

Для каждого элемента известно, из какого фрагмента текста он получился:
предложение, номер строки и смещения в символах. На этом держится двусторонняя
подсветка «текст ↔ схема» и колонка «исходник» в списке элементов.

Карта восстанавливается из предложения, которое сборщик записал в
`bpmn:documentation`, в три приёма: точный поиск от подвижного курсора (чтобы
повторяющиеся предложения не слиплись), поиск по всему тексту, и — как
последнее средство — привязка к строке. Поэтому элемент без соответствия
невозможен, и в интерфейсе не бывает «мёртвых» ссылок.

## Именование

Формулировки приводятся к конвенции BPMN — «глагол в инфинитиве + объект»:

```
Менеджер проверяет заявку   →  задача «Проверить заявку», дорожка «Менеджер»
Бухгалтер формирует счёт     →  задача «Сформировать счёт»
```

Источников два: словарь глаголов, реально встречающихся в описаниях процессов,
и набор суффиксальных правил. Если не сработал ни один — текст возвращается
**без изменений**. Неправильная форма глагола на схеме хуже, чем
непреобразованная, поэтому модуль никогда не угадывает. Полное отключение —
флаг `--verbatim-names` или `infinitiveNames: false`.

## Что делать, если понято не так

1. Нажмите **Анализировать** (или `bpmn-architect explain`) — увидите, во что
   превратилось каждое предложение.
2. Сверьтесь с таблицей маркеров в [RECOGNITION.md](RECOGNITION.md) и
   переформулируйте предложение.
3. Если нужна точность до элемента — опишите этот фрагмент на
   [DSL](DSL.md): оба синтаксиса попадают в один конвейер.
4. Либо постройте схему как есть и поправьте её мышкой — для этого редактор и
   существует.
